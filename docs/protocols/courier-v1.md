# Courier cryptographic API

This describes the Rust foundation. Courier service integration and platform delivery are tracked in the distributed-delivery plan.

All operations go through `deliveryCall(operation, args)` on an unlocked account. Native additionally checks the active vault owner. Web/Wasm uses the same Rust implementation. Arguments and schemas are bounded and reject unknown fields.

- `signEvent` takes scope, original message ID, original sent time, kind and a logical payload string. The returned immutable event signs the author, scope, ID, time, kind and payload hash under `chta delivery event v1`. `verifyEvent` checks the expected author, scope, payload and safe timestamp. Callers still enforce contacts and group membership.
- `nodeCertificate` creates or restores an installation's protected node state. A root signature certifies the random device signing key in a separate Courier domain. The node ID hashes that device public key; addresses are not node identities. `verifyNode` performs public verification without adding a friend.
- `newJob` takes a verified recipient, random 32-character hexadecimal job ID, scope, package count, current time and expiry. It generates a new content key and returns an opaque protected state, mailbox and public job bounds. Counts start at two, packages carry at most 256 KiB of plaintext, and retention is at most 24 hours.
- `encryptPackage` takes protected state, index, base64url plaintext and time. Rust generates a fresh 24-byte nonce and uses XChaCha20-Poly1305. Associated data binds the job, index, count, scope and expiry. The ciphertext leaf digest also binds the index.
- `packageRoot` takes ordered leaf hashes and one index. It returns a domain-separated Merkle root and that index's proof. Odd leaves duplicate themselves; proof length and duplicate-leaf values are checked exactly.
- `sealManifest` takes protected state, the signed event and private metadata: total payload size, content hash, package root, name and MIME type. Noise IK seals the small manifest and job key to the pinned recipient static key. The public carrier descriptor contains only version, random job ID, mailbox, expiry and sealed bytes. `openManifest` checks sender trust/static key, recipient, scope, job bounds and root, then returns recipient-protected state.
- `decryptPackage` verifies the manifest root/proof and AEAD binding before returning plaintext to the recipient. The receive pipeline must additionally verify total length, full-content digest and signed logical payload before committing history and issuing a receipt.
- `signControl` and `verifyControl` bind a fresh challenge, role, signer, expiry and bounded control body. Node roles sign advertisements, challenges and durable storage acknowledgements. Root identities sign allocations, deposits, pickup, recipient receipts, cancellation and repair controls. The service consumes challenges and validates each control body's operation-specific fields.

Protected state wraps keys inside Rust with an owner-derived, domain-separated AEAD key. It is stored again through the existing protected blob store. Plaintext node keys and content keys are never returned to Dart or JavaScript. It must not be copied to carrier indexes, advertisements or diagnostics.

Mailbox tags derive from the recipient root public key and a day bucket. They remain stable through phrase recovery, which can rotate the contact token. Pickup requires a matching root signature and a fresh challenge. Public-key knowledge can reveal a tag; these tags do not promise anonymity. Carrier indexes omit clear recipient DIDs and names.

Static-key offline sealing does **not** promise forward secrecy against later recipient-key compromise. Live session encryption stays unchanged. Couriers also observe connection timing, sizes and pickup associations. Two node certificates do not prove two independent operators.

The sender planner must enforce the separate two-node and never-full-set rules, including all historical allocations. Crypto acceptance alone does not establish distribution, durable storage, authorization to join a group, or recipient delivery.

`newJob` creates a fresh receipt challenge stored in sender-protected state and inside the sealed manifest. Only the intended recipient learns it from `openManifest`. A recipient receipt must bind that challenge, job ID, original message ID, manifest digest and received time. Unlike routing controls, a valid historical receipt remains verifiable after its transport expiry. Carrier retention is still bounded; a late proof never grants renewed storage or authorizes resurrecting deleted history.

Sender state uses immutable protected values, 256 hash-bucket index pages and a small two-phase root commit. Unpublished staged copies can be removed on restart; old readable commits remain referenced until their replacement is durable. The planner keeps exact bitmaps for at most 64 historical node certificates per job and waits rather than forgetting a privacy constraint. Storage acknowledgements remain distinct from recipient delivery.

Each job needs two certified Courier nodes under different routing identities. A relay forwards frames to all devices registered under the destination identity. The planner reserves each routing identity to its original certificate for the life of the job, including retries and rollout to replacement hosts. Courier pickup can still use a host on another device signed in to the recipient's identity. A cancellation is retried against assigned hosts until they confirm it or the deposit expires.

History repair runs over an authenticated live session. It compares 16 message IDs and digests per page, with a snapshot limit of 512 recent records or 512 KiB. The recipient saves the cursor after saving the page. Private repair covers text, including older text supplied directly by its original author. Group repair can restore signed text and file manifests visible to members at the original epoch and at reconnect. It examines the newest 512 group records and rotates through their epochs. Group files still use the verified piece transfer. For private attachments, the existing file transfer and Courier paths handle pending data. Repair does not recreate locally deleted messages and does not invent a receipt timestamp for recovered history.
