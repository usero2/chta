# Direct large file transfers

User approved the recommended direct-first encrypted transfer, relay fallback, bounded disk streaming, resume, and transport/rate/progress UI. Apply to chat attachments on Windows, Android and Web; retain existing identities and small media flows. This approved approach is the execution authority; routine interfaces below are implementation choices, not another approval gate.

## Approach
Use a separate authenticated WebRTC data channel for direct delivery on all three platforms, negotiated through the already authenticated encrypted chat channel. Keep Rust identities/private keys and encrypted cache. Google WebRTC DTLS encrypts the direct data channel; the verified Noise signaling channel binds its SDP fingerprints/session to the selected identity. Never reset/reuse the live chat Noise state to upgrade a file route. Keep existing relay/legacy transport as fallback. Embedding the Go Syncthing daemon adds a second identity/folder model and is unnecessary; raw QUIC alone would not support browser peers.

Direct limit: 10 GiB per file, relay limit remains 25 MiB. Old byte-backed attachments remain capped at 100 MiB. Large references/pickers use a separate 10 GiB bound. No whole-file buffering for streamed files. Above 25 MiB, a failed direct path pauses and retries direct, not silently moving bulk data onto relay. Web storage quota and destination capabilities may impose lower actual limits; surface precise errors.

## Storage and source contracts
`AttachmentSource` in chat/attachment_source.dart: length:int, key:String, openRead({int start=0,int? end}):Stream<List<int>>. ChatAttachment adds source-backed constructor, size/isStreamed/openRead; byte constructors/legacy JSON retain 100 MiB validation. Source-backed bytes must never be implicitly loaded. AttachmentRef adds nullable chunkedId/chunkSize, isChunked; only this metadata permits 10 GiB references. Preserve caption/group and owner isolation.

ChunkedAttachmentBridge in chat/chunked_attachment_bridge.dart exposes:
- beginChunkedAttachment(ownerId,id,size,chunkSize,{String? digest}) -> Future<ChunkedAttachmentState>
- chunkedAttachmentStatus(ownerId,id) -> Future<ChunkedAttachmentState>
- writeChunkedAttachment(ownerId,id,index,Uint8List bytes) -> Future<void>
- readChunkedAttachment(ownerId,id,index) -> Future<Uint8List>
- finishChunkedAttachment(ownerId,id,{String? expectedDigest}) -> Future<ChunkedAttachmentState>
- deleteChunkedAttachment(ownerId,id) -> Future<void>
State: id,size,chunkSize,contiguousChunks,completed,digest(nullable until finished). IDs 16..96 safe ASCII alnum/_/-, owner active for every operation. Size <=10GiB; chunkSize <=1MiB; standard 256KiB. Exact sequential writes, durable-before-progress, identical retry allowed, conflicting chunk rejected. Encryption AAD/entropy binds owner/id/index/size/chunkSize. Final SHA-256 checks incremental decoded chunks before complete. No arbitrary disk paths cross the cache API. Native uses existing protection, browser encrypted IndexedDB chunks/nonextractable key. Quota/error must not claim completion. `createChunkedAttachmentBridge({Object? bridge})` returns nullable capability (native bridge or Web adapter); unsupported fakes remain legacy.

`ChunkedFileCache(bridge)` high-level bounded helper: importStream(owner,id,size,Stream<List<int>>, {chunkSize=262144}) -> state; openRead(owner,id,{start=0,end}) -> stream. Import durably spools selection before history/send so picker grants are unnecessary for later resume. Browser hashing must remain incremental (Dart crypto), not WebCrypto whole-file digest.

## Direct link
`DirectFileLink` in p2p/direct_file_link.dart, injectable peer/datachannel adapter. Constructor ownIdentityId, sendSignal(String id,String text); frames stream; changed stream or callback; peerId/ready; bind(String? peerId,{required bool signalingAvailable}); receiveSignal(String id,String text); send(String frame); close(). Negotiate offers/answers/ICE through reserved `cht-control-direct-v1-` encrypted controls after verifying both peers advertise signed `files-v2`. Deterministic initiator, random session, bounded descriptions/candidates/frame buffers, stale-peer generation checks before/after awaits, datachannel output backpressure. Only STUN, no TURN configured, so ready means direct, never label a relay candidate Direct. Retry failures while signaling exists. A live authenticated DTLS link survives loss of the rendezvous relay; explicit identity/peer change closes it. No camera/audio track access/permissions for data-only use.

## Transfer and history
V2 reserved packets have a distinct namespace and never enter visible chat/legacy receipt handling. Offer includes stable message/transfer id, complete digest, size, cache block size, name/mime/presentation and sent time. Receiver cache id derives from peer+wire id to prevent cross-peer reuse. Validate metadata and transport policy before allocating/writing. Resume from durable contiguous block count. Each 256KiB cache block is split into <=8KiB wire pieces; sender keeps at most a small bounded window, receiver stores at most bounded blocks. Authenticate and hash blocks, persist before confirming durable progress. A complete file requires final SHA-256 and history persistence before Delivered. Identical retries resume/deduplicate; mismatched metadata and corrupt cache fail safely. Session/identity switches cannot deliver into another conversation. Persist outgoing/incoming refs and pending state; automatic resume after reconnect/restart from history. Explicit retry remains available. <=25MiB may fall back to existing encrypted relay. Older peers do not receive v2 control text or oversized file offers.

Progress snapshot: confirmedBytes,totalBytes,bytesPerSecond,transport (Direct/Relay),phase (preparing/sending/receiving/waiting/completed/failed). Show under the file card, no offline banner while a verified direct link is usable. File export streams to native file/Android SAF output or browser writable destination; do not fall back to all-bytes save for large files. Large media uses bounded preview or safe generic file card if no streaming renderer is available; small media/markdown remain unchanged.

## Verification
Use synthetic files and disposable identities only. RED/GREEN tests: encrypted chunks/tamper/owner switching; >100MiB bounded source and exact hashes; disconnect/recreation resume without retransmitting durable blocks; corrupt/duplicate/mismatched offers; direct-to-relay policy; stale callback/session swaps; legacy small media; browser quota/export unsupported cases. Exercise native and browser WebRTC pairs, identity-bound negotiation, direct without relay after rendezvous, stats and transfer of a synthetic >100MiB file. Build version25 for all platforms and deploy Android without erasing data. Do not send real contact messages or enter PIN/phrase or change actual PIN preference.
