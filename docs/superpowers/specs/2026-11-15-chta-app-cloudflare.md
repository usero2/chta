- wss://chta.app/relay is a separate discovery/signaling protocol, NOT a /cht data relay. HTTP GET returns safe mode/health metadata; nonupgrade POST and uploads rejected. Seed helps authenticated identities find an existing verified friend and obtain signed public data-relay records. Never expose an enumerable list of all users or their contacts. No user-message, file, file-name or attachment frames accepted. No offline mailbox.

If NAT prevents Direct and no data relay exists, show waiting/reconnect, never fall back to sending content over seed. Changing domains does not sync an existing identity automatically; recovery remains client-side.

## Seed wire v1 — exact shared contract
Text JSON only. Endpoint /relay; maximum frame 16384 UTF-8 bytes; max 1000 registered sockets (env override within sane bound), 4 per DID; per-socket challenge expires 30s. Rate limit bounded by socket and IP; never trust forwarded sender fields. String IDs exact did:cht:[0-9a-f]{64}. Seed ID = SHA256 UTF-8 `chta.app/relay/v1` (64 lowercase hex); nonce 32 random bytes base64url without padding.
- Server challenge: {type:"challenge",protocol:"chta-seed",version:1,seedId,nonce}.
- Client register: {type:"register",proof:<existing Rust RelayProof object>} (relayProof(nonce,seedId)). Verify Ed25519 signature and SHA256 public key matches DID using existing domain `cht relay registration v1\0${seedId}\0${nonce}`. One-time challenge, no repeated registration/replay. Reject before registration everything except closing.
- Server registered: {type:"registered",protocol:"chta-seed",version:1}; then {type:"catalog",records:[<RelayRecord>]} (max64 per batch).
- Client lookup {type:"lookup",identityId}; server presence {type:"presence",identityId,online:boolean}; no list-all API. Only route signals to registered recipient, no self signal; offline => {type:"unreachable",identityId}. Limit lookup rates; verification of actual friendship happens at recipient before signaling acceptance.
- Client {type:"catalog",records:[<signed RelayRecord>]} accepted max64, global known records max1000, strict current RelayRecord v1 signature/TTL/public /cht URL validation, recheck expiry on serve. No arbitrary user-provided fetches. Records use existing Rust canonical payload `cht relay directory v1\0` + JSON tuple [version,relayId,publicKey,endpoint,issuedAt,expiresAt]. Expired hints removed, signatures never minted by seed.
- Client/server signal {type:"signal",envelope:<SeedSignal object>}. Sender must equal authenticated proof DID. Validate full schema, signature, timestamp, ID/SDP/candidate constraints before routing. No opaque encrypted body or generic route frame.
- Keepalive client {type:"keepalive"}, server {type:"alive"}; use WebSocket automatic response for exact serialized strings. Invalid/binary/oversize/flood closes with policy code; bound memory and in-flight async validation across hibernation/socket closure.

SeedSignal object (deny unknown fields): {version:1,from,to,session,id,kind,payload,issuedAt,expiresAt,publicKey,signature}. session 32 lowercase hex. id is existing DirectFileLink control ID `cht-control-direct-v1-${session}-${kind}-${counter}`; counter decimal, kind offer|answer|ice. payload is original DirectFileLink JSON text {v:1,t:kind,s:session,d:SDP} or {v:1,t:"ice",s:session,c:candidate,m:nullable string,l:nullable integer}. Deny extra payload fields. SDP <=11000 bytes with SHA256 fingerprint and valid offer/answer role; candidates <=2048, reject typ relay; nullable mid<=64 and line integer0..65535. Entire envelope <=16384 bytes; payload <=11264 UTF8 bytes. issuedAt/expiresAt exact safe nonnegative integer milliseconds; max lifetime120000ms; issuedAt <= now+30000, expiresAt>now. from!=to. publicKey32/signature64 base64url bytes, DID hash matches key. Signature payload is UTF8 `chta seed signal v1\0` followed by JSON tuple [version,from,to,session,id,kind,payload,issuedAt,expiresAt]. from/to/session/id/kind/payload/time all signed. End-to-end recipient verifies expected verified-contact public key AND to==active owner, not merely seed's authentication claim. Deduplicate/reject replay per sender+id+signature within bounded TTL map; no private keys in Dart or JS.

## Shared bridge API (crypto worker owns)
New lib/seed/seed_crypto_bridge.dart:
abstract interface class SeedCryptoBridge {
 Future<String> signSeedSignal(String peerId,String messageId,String text,int now);
 Future<String> inspectSeedSignal(String source,String expectedPeer,int now);
}
sign returns SeedSignal JSON; inspect returns JSON {peerId:<from>,messageId:<id>,text:<payload>} after active-owner and verified-contact key binding. Both Rust AccountCore, Native commands, WASM exports, chtCore loader and Native/WebCoreBridge implement same names. Native args sign {peerId,messageId,text,now}; inspect {source,expectedPeer,now}. Private keys stay Rust, nonce/timestamps checked there. Add signed `seed-v1` contact capability. Existing relayProof API unchanged. Deterministic test vectors consumed by JS server tests must live under shared fixtures; coordinate before adding.

## Client ownership/integration (Flutter worker owns)
New SeedClient using injected RelayConnector/AccountBridge+RelayCryptoBridge+SeedCryptoBridge and endpoint default wss://chta.app/relay (CHT_SEED_URL override). Registers unlocked owner, selects only verified contact, reconnects bounded exponential backoff, generation-scopes all async work, stops/disposes on identity lock/switch. Exposes registered/status/presence and verified incoming signals; publishes/ingests existing signed relay records through RelayNetwork validation. Seed is not inserted into data-relay list, normalizer /cht unchanged. UI shows seed status separately and concisely. Seed connects automatically after unlock; no invite/join required for an existing verified friend. No auto-add/auto-verify stranger.
Reuse PeerFileController/DirectFileLink rather than duplicating data channels. When normal authenticated Noise control exists retain it; otherwise use end-to-end signed seed signals. A successfully signed/verified seed signal may negotiate with an existing verified contact even if its older saved card lacks seed-v1/files-v2, but never assume a DTLS link authenticated before remote SDP envelope signature validation. Shared selected-peer generation and route binding must survive awaits. Normal fallback messages/files remain on authenticated data relays only; seed cannot set encrypted Noise-authenticated=true. Separate signaling authentication from bulk fallback authentication explicitly. Direct receipts/history/progress and 10GiBDirect/25MiBrelay policies unchanged.
